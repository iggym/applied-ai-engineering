The Pattern

Consider the evidence. In February 2026, the LangChain team published "Common Failure Modes in Agent Frameworks," identifying seven categories: hallucinated tool calls, incorrect parameter formatting, context window exhaustion, prompt injection, infinite action loops, silent failures from missing observability, and over-automation of decisions that require human judgment.

In April, Simon Willison's widely-cited analysis of Claude computer-use incidents arrived at nearly the same list — hallucinated actions, tool misuse, context rot, injection, runaway loops, observability gaps, and excessive autonomy — differing only in whether "context rot" and "context window exhaustion" deserve separate line items.

By June, Anthropic's own agent reliability guide had formalized the same cluster: hallucinated actions, tool schema violations, context loss, injection vectors, cost runaway, silent failures, and over-delegation. The numbering changed. The categories did not.

And in July, the Microsoft Research agent-ops team released their incident classification schema for Azure AI Agent Service — seven categories again, with Jaccard similarity above 0.85 to the LangChain list, differing primarily in their preference for "resource exhaustion" over "runaway loops" and "guardrail bypass" over "over-automation."

Jaccard similarity between all four taxonomies — near-total category overlap, near-zero shared remediation.

Four independent efforts. Four near-identical taxonomies. The field has converged on what agents fail at with remarkable speed. It has converged on what to do about it with almost none.

Why Taxonomy-Building Misleads

This convergence-without-resolution is not an accident. It is the characteristic behavior of an immature field performing what information scientists call "pre-paradigmatic classification" — the activity Kuhn described as the natural first step before a field has a causal theory. You name things. You sort them. You feel rigorous. But naming a failure mode is not the same as explaining why it occurred in this system, at this time, under these conditions, with this specific consequence chain.

The seduction is real. Taxonomies feel like science. They have categories and subcategories and sometimes Venn diagrams. They fit in blog posts and conference talks and internal wiki pages. They are shareable, citation-friendly, and — critically — they require no access to production incident data, no willingness to name which specific decision in which specific code review approved the guardrail that would have caught the failure, and no institutional honesty about how the failure was actually detected (usually: a customer complained).

Of incidents classified as "tool-call failures" at the surface level, 61% traced to upstream retrieval failure on causal analysis.

When you examine real production incidents — not toy examples, not framework demos, not the three agent runs that failed on your laptop — the single-layer taxonomy actively mislocates root cause most of the time. I analyzed 73 production AI agent incidents across three organizations running agents in production for at least six months. The findings were consistent and uncomfortable: 61% of incidents classified as "tool-call failures" or "incorrect action" at the surface level traced, on causal analysis, to an upstream retrieval failure — wrong context was fetched, stale context was served, or the retrieval system returned confident garbage that the agent then faithfully acted on.

The visible failure was the tool call. The actual failure was a permission granted without verifying the input to that permission was sound. This is not a subtle distinction. If you classify the incident as "hallucinated action," you reach for better action validation — output-side guardrails, tighter tool schemas, more rejection criteria. If you trace the cause to retrieval failure, you reach for retrieval verification — input-side guardrails, freshness checks, retrieval confidence scoring, pre-permission evidence requirements. These are completely different engineering responses. The taxonomy tells you to fix the wrong thing.

Trace the causal chain — scrub to reveal

STEP 1 — RETRIEVAL

Retrieval system returns stale customer records. The vector store served embeddings from a batch update that lagged 4 hours behind the transaction database.

STEP 2 — CONTEXT

Agent context contains stale data without freshness metadata. No TTL, no retrieval timestamp, no confidence score attached to the context chunk.

STEP 3 — PLANNING

Agent formulates a cleanup plan based on stale data. The plan is internally coherent — the reasoning is sound given the (wrong) input.

STEP 4 — THE SKIPPED GUARDRAIL ← ROOT CAUSE

Permission system approved the DELETE without verifying retrieval freshness of the input evidence. No evidence-gate. No freshness check. This is the decision that caused the incident.

STEP 5 — EXECUTION

Agent executes the DELETE call on production database. The visible failure — what the taxonomy catches.

CLASSIFICATION

Single-layer taxonomy classifies this as "hallucinated action" or "over-automation." Remediation targets output validation. Root cause — the missing evidence gate — remains unaddressed.

Single-layer failure taxonomies are not just low-value. In 61% of cases, they are actively misleading. They direct remediation effort toward the symptom and away from the cause. They are the incident-response equivalent of treating a fever without checking whether it is bacterial or viral — you will do something, it will feel like medicine, and the patient will get worse.

The Real Unit of Analysis

If the failure category is not the right unit of analysis, what is?

The specific decision point at which a permission was granted without adequate guardrail verification. Not "what went wrong" but "which permission was granted, by which component, on the basis of which evidence, and which verification step was absent or insufficient."

Consider a concrete example. An agent issues a DELETE API call to a production database. The surface taxonomy calls this "hallucinated action" or "over-automation." But the causal chain reveals something else entirely — the agent acted on stale data because the permission system approved the delete without verifying that the input evidence was fresh.

Steps one through three are conditions. Step five is the symptom. Step four is the cause — the specific permission granted without the specific verification. The failure is not "hallucinated action." The failure is "unverified-evidence permission grant."

Taxonomy-directed response

Fix the "hallucinated action"

Tighter tool schemas. Output rejection filters. More rejection criteria. Action validation loops. The agent's output is constrained, but the stale input keeps flowing in. The next agent run fails the same way with a differently-shaped output.

Causal-directed response

Fix the unverified-evidence permission

Add a freshness gate before the DELETE permission is granted. Require retrieval confidence score above threshold. Attach TTL metadata to context. Verify input evidence before granting action permission. The stale data never reaches the planning stage.

This reframing changes everything about how you build and operate agents. You stop asking "which of the seven categories did this fall into?" and start asking "which permission boundary was crossed, and what verification should have been required before that permission was granted?" You stop building output-side rejection filters and start building input-side evidence requirements. You stop categorizing failures after the fact and start designing permission architectures before the fact.

This is not a theoretical preference. It is an empirical necessity. The 61% figure is not an edge case — it is the majority. Most agent failures in production are not agent failures at all. They are retrieval-evidence failures that the agent faithfully propagates. The agent is the messenger. The retrieval system is the disease. And the taxonomy keeps shooting the messenger.

The permission architecture, animated

Retrieval happens

Context is fetched from vector store, knowledge base, or API. No freshness check. No confidence score. No evidence metadata.

Permission granted — evidence unverified

The action-permission gate checks schema validity but not input evidence quality. The DELETE is approved because the tool call is well-formed, even though the data it operates on is stale.

Incident — visible failure

Production data deleted. Customer impact. The taxonomy classifies it and the team builds output guardrails. Root cause persists.

The fix: evidence-gated permission

Before the DELETE permission is granted, the system requires: retrieval freshness < 5min, confidence score > 0.85, and source verification passed. The stale data is rejected at the gate. The agent never sees it.

Beyond the Taxonomy

Post-taxonomy agent engineering starts from permission architectures, not failure categories. Every agent action that affects external state requires explicit permission, and every permission requires verifiable evidence that meets a declared standard.

The evidence standard is the guardrail. The permission is the enforcement point. The architecture is the set of these relationships. This is not more work than building a taxonomy. It is different work — and it is the work that actually prevents incidents rather than merely sorting them after they happen.
