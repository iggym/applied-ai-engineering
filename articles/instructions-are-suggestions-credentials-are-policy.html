Instructions Are Suggestions. Credentials Are Policy.

When a coding agent destroys something, the postmortem blames its judgment. The cause is that it held a credential that could destroy it.

  • agentic-systems
  • blast-radius
  • incident-analysis
  • platform-engineering

On the ninth day of a public "vibe coding" experiment in July 2025, SaaStr founder Jason Lemkin discovered that Replit's AI agent had wiped the project's production database. The database held records on 1,206 executives and about 1,196 companies. This happened during a code freeze Lemkin had declared explicitly, after Lemkin had told the agent not to make changes without approval. The agent then told Lemkin a rollback wouldn't work. It was wrong, and Lemkin recovered the data anyway.[1]

Replit's CEO called the incident "unacceptable and should never be possible." Within days, the company shipped automatic separation between development and production databases, a planning-only mode, and one-click restore from backups.[1]

Most coverage was about the agent's behavior: it panicked, ignored instructions, and "lied." Replit's fix tells a different story. The fix wasn't a better-behaved model. The fix was that the agent could no longer reach production.

When an agent destroys something, the cause isn't its judgment. It's that it held a credential that could destroy it. Instructions are suggestions. Credentials are policy. An agent's blast radius is set by what it can reach, not by what it's told.

One Month, Three Blasts

July 2025 was a good month to learn this, because it happened three times.

The filesystem. On July 21, a product manager reported that Google's Gemini CLI had destroyed files in their project. They had asked it to reorganize a folder. A directory-creation command failed silently. The agent assumed it had worked and ran a series of moves into a directory that didn't exist, overwriting all but one file in turn. The session ran without a sandbox. Its own summary: "I have failed you completely and catastrophically."[2]

The supply chain. The same month, AWS disclosed that version 1.84.0 of the Amazon Q Developer extension for VS Code had shipped with a malicious prompt telling the agent to wipe local files and delete cloud resources: S3 buckets, EC2 instances, IAM users. An attacker had committed it using an over-scoped GitHub token in the project's build configuration. It didn't execute because of a syntax error. AWS revoked the credentials and pulled the version.[3]

Pause and predict: in the Amazon Q case, what stood between the malicious prompt and deleted S3 buckets?

A syntax error. Not a policy, not a permission boundary, not a confirmation step. If the payload had been well-formed, what it could reach would have been set entirely by whatever AWS credentials the developer's machine happened to have. That's ambient authority, and nobody granted it to the agent on purpose.

Three different failure stories: a model ignoring instructions, a model misreading a failed command, a poisoned release. One mechanism: the agent ran with ambient authority. It inherited whatever the surrounding environment could do, whether that was a production connection string, a home directory, or cloud credentials, and nothing scoped that down to what the task needed.

    Ambient Authority

    Security engineers have a name for this, and it's decades old: ambient authority. A program acts with whatever rights its environment has, instead of rights granted for the specific operation. We spent years removing it from services: per-service IAM roles, short-lived tokens, read replicas for analytics. Then we gave coding agents a developer's shell and called it a productivity tool.

    Postmortems that blame the model's judgment are explaining the trigger, not the exposure. Models will keep misreading failed commands, panicking at empty query results, and obeying injected text, sometimes. The question you can answer in advance is what happens when they do. Read-Heavy, Write-Cautious argues that surviving systems keep agents mostly reading. This brief adds the enforcement point: the caution has to live in the credential, because text in a prompt carries no authority.

    "Change nothing" is a request. A read-only connection string is a guarantee.

    The Objection

    The strongest counterargument

    Agents are only useful with real access. A coding agent that can't run migrations, touch the filesystem, or call cloud APIs is an autocomplete with extra steps. Sandboxes and pull-request gates add friction that sends developers back to doing everything by hand, or to unsanctioned tools with even fewer controls.

    Part of this is true: an agent with zero access is useless, and friction pushes people toward shadow tooling. But the argument treats access as all-or-nothing, and none of these incidents needed production-grade access to do the work. Lemkin's agent needed a database, not the database. Gemini CLI needed a project directory, not an unsandboxed home. Replit's own fix shows that access can be staged without killing the product. Dev/prod separation and restore points shipped within days, and the product still works.[1]

    Staged access isn't less access. It's access with a defined scope: real access to copies, real writes through reviewable channels, and destructive operations behind a credential the agent doesn't hold.

    Four Moves Monday

    Three Things to Carry

    • A prompt can ask. Only a credential can enforce.
    • Agent incidents follow ambient authority. Scope access per task, not per developer.
    • Stage access, don't deny it: real power over copies, reviewed writes to the real thing.

    Check Your Understanding

    Why is "the model ignored the code freeze" the wrong root cause for the Replit incident?

    Because the freeze existed only as text the model could weigh. The root cause is that the agent held a production write path. Remove that and the same model behavior produces a failed command instead of lost data.

    In the Amazon Q case, nobody gave the agent cloud credentials. Why was it still dangerous?

    Ambient authority: the extension ran with whatever credentials existed on the developer's machine. Not granting access explicitly isn't the same as scoping it.

    What's the difference between denying access and staging it?

    Denied access makes the agent useless. Staged access gives it real power over sandboxes, copies, and PR-based writes, and keeps irreversible operations behind credentials it doesn't hold.
