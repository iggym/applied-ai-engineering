Read-Heavy, Write-Cautious

Across seven field-notes repos, the production systems that survived contact with real users share one design instinct — and it isn't the one vendors sell you.

The Volume and The Handoff

When Klarna deployed their AI assistant, the headline was massive: 2.3 million customer chats handled in a single month, matching the output of 700 human agents. The CEO pitched it as an autonomous triumph. The engineering team knew a different reality. A full third of those interactions—touching refunds, account modifications, and payment disputes—were quietly routed to humans. The AI could read the customer’s frustration perfectly, but it wasn't allowed to touch the ledger.

This is the pattern that keeps showing up across the production systems that actually survive contact with users. The vendors sell you autonomous agents that spin up, reason, and act. The practitioners who deploy them build something else entirely.

The Traction of Asymmetry

The surviving pattern is read-heavy, write-cautious. [QUOTE 3] Vendors sell the tire-spinning autonomy of a sports car; practitioners build the deliberate, asymmetric traction of a tractor.

In database engineering, we don’t let every process commit to the database whenever it feels like it. We use ACID transactions. We separate reads from writes. We lock rows. We enforce commit boundaries. [BEAT 1] When we look at why autonomous AI agents fail in production, we blame their reasoning capabilities. But they aren't failing because they can't think. They are failing because they lack transaction boundaries. We stopped trying to teach the agent how to think and started teaching it how to stop. [QUOTE 1]

Consider GitHub’s Copilot Workspace. When they moved from inline autocomplete to multi-file generation, they didn't just let the agent write code. They forced an intermediate step: a plan. The agent reads the repository, drafts a specification, and halts. The human reviews the plan. Only then does the agent write the code. Adding this 15-second human review slowed down the write speed but doubled the code acceptance rate.

[BEAT 2] Engineering leaders often view human-in-the-loop as a temporary crutch for models that aren't smart enough yet. This is a fundamental misread of system design. The model writes the draft, but the human holds the commit key. [QUOTE 2] Human-in-the-loop isn't a patch for stupidity; it is a permanent architectural requirement for safe state mutation.

The agent stops writing continuously. It enters a read-heavy state, gathering context until it hits a defined, interruptible write node. The system changes from a continuous stream to a batch process.

Drafts and Commit Keys

The strongest counterargument is that models will eventually become reliable enough to write autonomously. If GPT-6 can write flawless code or execute perfect refunds, the commit boundary is just latency. But this ignores the nature of production environments. Environments drift. Database schemas change. Edge cases exist outside the training distribution. A genius agent with no commit boundary is a liability, because autonomy scales the execution of tasks, but asymmetry scales the survival of the system. [QUOTE 4]

LangChain’s ecosystem pivot proves this. In 2024, practitioners abandoned free-form autonomous loops in favor of LangGraph. They realized that agents spinning in continuous write loops hallucinate catastrophically. By wrapping agents in a state machine, engineers forced the agent into long read phases, punctuated by sharp, interruptible write nodes. They domesticated the agent by restricting its write access.

The Illusion of Autonomy

Vendors measure success by "tasks completed." Practitioners measure success by "rollback rate." If you don't know your agent's rollback rate—the percentage of actions that have to be undone by a human or a script—you are flying blind. A high task completion rate means nothing if your engineering team is spending their weekends writing scripts to reverse agent actions.

Auditing the Write Path

You cannot fix an agent that writes too much by making it smarter. You fix it by restructuring its interface with the world.

1. Audit the Write Frequency: Count how many state-mutating API calls your agent makes per session. If it is more than one or two, you have an architectural flaw. Bundle those writes.

2. Implement Plan-Review Interrupts: Before any write operation, force the agent to output a JSON payload defining its intent. Block the write until a human or a deterministic rule approves it.

3. Measure Rollback Rate: Track how often agent actions are reversed. Make this the primary KPI for your agentic pipelines, not tasks completed.

Count the Commits

Tomorrow morning, pull the logs for your most deployed agent. Count the write operations it executed in the last 24 hours without an explicit human approval gate. If that number is higher than you are comfortable with, you know exactly where to build your next transaction boundary.
